## 🔴 严重

### 1. App 订阅 `currentTimeMs`，播放时整棵树按 timeupdate 频率重渲染——而且订阅产物是死代码

App.tsx:267：

```ts
const playheadMs = useStore((s) => s.currentTimeMs);
const playhead = playheadMs / 1000;
```

`currentTimeMs` 在播放中持续变化（playback.ts 已做同值短路，但播放时值必然变）。每次变化触发 App 整体 re-render：2598 行函数体重新执行、几十个 inline 闭包重建、4 个面板（均未 memo）全部重渲染。

而 `playhead` 在 App 渲染路径上的两个消费点都是死代码（已用 grep 全文件验证）：
- App.tsx:650 `playheadLocal` → 只被 App.tsx:2370 `playheadPercent` 使用
- `playheadPercent` 在 JSX 中零引用（A4-3 把 overlay 移进了 ReviewPanel，这两行漏删了）

真正需要 playhead 的三处都不需要 App 订阅：自动暂停 effect（App.tsx:1289-1297）、`updateTrimRange` 内的 `nextPlayhead`（App.tsx:1632，同函数里 `seekRelative` 已示范正确做法 `useStore.getState().currentTimeMs`）、ReviewPanel/TimelineSurface 自己订阅了。

**建议**：删除 App.tsx:267-268 的订阅、:650 和 :2370 的死变量；`updateTrimRange` 改用 `useStore.getState()`。自动暂停 effect 改为 `useStore.subscribe` 形式，或下沉到 PlayerSurface 的 `onTimeUpdate`。这是改动最小、收益最大的一处：改完后播放过程中 App 完全不重渲染。

### 2. 轮询每 tick 全量替换引用：导出期间每 250ms 一次全 UI 重渲染

App.tsx:1043-1050。链条如下，即使后端返回的数据内容完全没变也成立：
1. `setJobs(response.jobs)` → jobs.ts:51 `set({ jobs: [...next] })` 必产新数组；`setProject(nextProject)` 每次都是新对象。
2. `videos`/`clips`/`activeJobs` 引用全变 → App 的 ~30 个 useMemo 全部重算（`filteredClips` 重新 filter+sort、`groupedFilteredClips` 重建分组……）。
3. 所有面板 props 引用变化 → 全部重渲染，`React.memo` 也救不了。
4. 副作用：deps `[activeJobs, videos]` 每 tick 都变 → interval 每个周期被 clear + 重建，实际退化成 setTimeout 链。

导出时 250ms 一次，正好叠加在用户继续审片的场景上。

**建议**：在 set 之前做内容短路——比较 `project.updated_at` + `jobs` 的 `(id, status, progress)` 摘要；相同则直接 return。轮询 effect 的 deps 收敛为布尔值（`hasActiveWork`、`hasActiveExportJob`）。

### 3. `refreshProject` 的 silent 选项不抑制错误提示

App.tsx:892-907：`silent` 只 gate 了 `setIsLoading`，没 gate `setErrorMessage`——对照 `refreshJobs`（App.tsx:913-917）是有 `if (!options?.silent)` 的。后果：检测/导出期间后端瞬时不可用，每 250ms~1s 弹一个错误 toast，且每个错误 toast 会顺带清掉成功消息（App.tsx:995-1000）。**一行修复。**

## 🟡 重要

### 4. 轮询无 in-flight 防护与响应排序，旧响应可覆盖新状态

`refreshWorkspace` 每 250ms 发起 `fetchProject`，没有 in-flight guard 和响应序号。后端响应 > 250ms 时请求堆积，乱序返回的旧 project 快照会覆盖新的；用户 PATCH 返回的新 project 可能被更早发出、更晚返回的轮询 GET 覆盖回旧值。trim 场景下 App.tsx:1260 的 autosave effect 会自愈，但表现为边界回跳闪烁 + 多余写库。

**建议**：模仿 TimelineSurface 已有的 `fetchSeqRef` 模式——单调递增 seq，过期响应丢弃；in-flight 期间跳过新 tick。配合 #2 的 `updated_at` 比对可彻底消除回退。

### 5. ReviewPanel 整体按播放频率重渲染，inline render prop 阻断子组件优化

ReviewPanel.tsx:131-132 订阅 `isPlaying` + `currentTimeMs`，播放中整个面板按 timeupdate 频率重渲染，但真正需要播放头的只有 overlay 进度条（:186）和时钟读数（:190、:282）。同时 :243-245 每次渲染新建 `renderActiveSegmentHandles` 闭包和 `onScrubMove` 箭头函数，会击穿未来的 memo。

**建议**：把 `currentTimeMs` 订阅下沉到两个叶子组件；回调用 `useCallback` 固定后给 TimelineSurface 加 memo。

### 6. tsconfig 无 strict 模式

tsconfig.json 没有 `strict`、`strictNullChecks`、`noImplicitAny`、`noUnusedLocals` 中的任何一项。`npm run lint`（tsc --noEmit）目前只做最基础的结构检查；所有 `xxx | null` 字段的解引用都不会被检查。

**建议**：渐进式开启——先 `noUnusedLocals` + `noFallthroughCasesInSwitch`，再 `strictNullChecks` 按目录分批修。

### 7. trim 状态三套账本并存

App.tsx:253-254 `useState`（渲染源）、:285-286 `trimStartRef/trimEndRef`（rAF 回调用）、store/trim.ts 的 `startMs/endMs`（无人写入，trim.ts:42-50 的 TODO 自己承认零调用方）。连带效应：键盘 effect（App.tsx:1299-1418）deps 里有 `trimStart/trimEnd/project/activeSegment`，每次微调和每次轮询 tick 都重挂 window keydown 监听器。

**建议**：完成 TODO M1 接线，删掉 useState + ref 两套；键盘 effect 改为挂载一次 + `useStore.getState()` 读实时值。

### 8. 拖拽缺 `pointercancel`，中断时 document 监听器泄漏并持续 seek

TimelineSurface.tsx:182-183 与 App.tsx:1850-1851 两处都只在 `pointerup` 移除 document 监听器。指针被系统取消（触控板手势、窗口失焦、Electron 弹窗）时 `pointerup` 不触发，document 上的 `pointermove` 监听器永久残留，之后每次移动鼠标都在持续 `enqueueSeek`。

**建议**：补 `pointercancel`；更稳的做法是 `setPointerCapture(e.pointerId)` + 元素级监听。

### 9. 列表无虚拟化、面板无 memo

一场全锦赛单视频可产出上百候选片段。顺序很重要——先修 #1/#2 稳定 props 引用，再给两个面板加 `React.memo`；片段总量预期超过 ~200 时引入 `@tanstack/react-virtual`。key 用法已正确。

# 二、Electron 主进程 / preload / 构建配置审查

**总体印象**：整体安全基线比同类单人项目好不少：`contextIsolation: true`、preload 暴露面精确收敛、密钥走 `safeStorage` 加密、后端绑 `127.0.0.1`、Sentry 有 `beforeSend` 脱敏、`windowsHide` 已正确处理。主要风险集中在三处：①本地 HTTP 服务无鉴权 + 缩略图接口目录穿越；②后端子进程孤儿风险 + 端口固定 8000；③缺导航拦截与单实例锁。

## 🔴 严重

### 1. 缩略图接口目录穿越——可读取磁盘任意文件

`backend/video_review_backend/thumbnail_service.py:63-64` + 路由 `routers/videos.py:337-342`：

```python
def resolve_file(self, video_id: str, file_name: str) -> Path:
    return self.cache_root / video_id / file_name   # ← 无校验直接拼接
```

`video_id` 和 `file_name` 都来自 URL path 参数，未做任何归一化校验。结合第 2 条（服务无鉴权、CORS `*`），本机任意进程 / 任意网页都能通过 `..%2f` 编码逃出 `cache_root` 读任意文件。这是任意文件读取，配合无鉴权 = 本机任何代码可借这个 App 当文件读取代理。

**建议**：解析后强制校验落点在 `cache_root` 内，并拒绝带分隔符的 `file_name`：

```python
def resolve_file(self, video_id: str, file_name: str) -> Path:
    if "/" in file_name or "\\" in file_name or ".." in file_name or "/" in video_id:
        raise HTTPException(400, "invalid name")
    base = (self.cache_root / video_id).resolve()
    target = (base / file_name).resolve()
    if not target.is_relative_to(base):   # py3.9+
        raise HTTPException(400, "path escape")
    return target
```

`/stream`（videos.py:282-293）和 `get_thumbnail_file` 也建议统一走这套校验。

### 2. 本地 HTTP 服务无鉴权 + CORS 全开

`backend/video_review_backend/api.py:33-38`：`allow_origins=["*"], allow_methods=["*"], allow_headers=["*"]`。

后端绑 `127.0.0.1`（main.py:59 + main.cjs:175），外网访问不了，但本机任意进程、以及用户浏览器里打开的任意恶意网页都能直接打 `http://127.0.0.1:8000/api/...`：跨域读项目数据、触发导出、触发检测（消耗智谱 API key 配额）、配合第 1 条读任意文件。对桌面 App 这是经典的 localhost CORS 攻击面。

**建议（最小改动）**：① `allow_origins` 收紧成实际渲染源；② 加 `GYMCLIP_API_TOKEN`（spawn env 生成随机值），后端中间件校验 `X-Gymclip-Token`，前端请求统一带上，token 经 preload 以 `contextBridge` 暴露。

## 🟡 重要

### 3. 后端子进程：SIGKILL / 崩溃路径下孤儿进程风险

`main.cjs:877-882`：`before-quit` 只发 SIGTERM，不等待、不补刀 SIGKILL。后端若卡在 ffmpeg 子进程或 uvicorn 关闭钩子上就成孤儿，继续占 8000 端口。主进程被 SIGKILL / 崩溃时 `before-quit` 根本不触发。后端自己 spawn 的 ffmpeg/ossutil 子进程也不在受控范围。

**建议**：① SIGTERM 后设 3s 超时补 SIGKILL；② 后端侧加"父进程消失即自杀"看门狗（轮询 `os.getppid()==1` 或读 spawn env 传的主进程 pid）；③ Windows 上 `kill('SIGTERM')` 不杀子进程树——win 下用 `taskkill /pid <pid> /T /F`。

### 4. 固定端口 8000，无随机/冲突回退

`main.cjs:176`。当前靠 `ensureBackendCompatibility`（main.cjs:622-632，检查 `/openapi.json` 里有没有 `/api/platform/matches`）识别占端口者，是很脆的启发式。

**建议**：启动前探测端口可用性，被占用就在 8000–8099 找空闲端口，经 env 传给后端。

### 5. 缺少导航拦截与 window.open 处理

`main.cjs:682-705` 无 `setWindowOpenHandler` 也无 `will-navigate` 拦截。Electron 安全基线标配：

```js
window.webContents.setWindowOpenHandler(({ url }) => {
  shell.openExternal(url);
  return { action: 'deny' };
});
window.webContents.on('will-navigate', (e, url) => {
  if (url !== window.webContents.getURL()) e.preventDefault();
});
```

### 6. 没有单实例锁——双开必端口冲突

全文无 `app.requestSingleInstanceLock()`。双开时第二个实例撞 8000 端口，最坏两个 Electron 抢同一份 `userData/workspace` 状态文件（`project_state_lock` 只在单进程内有效，跨进程不互斥）→ 项目状态可能损坏。

### 7. dev 服务器绑 `0.0.0.0`，局域网可访问

`package.json:15` `"dev:web": "vite --port=3000 --host=0.0.0.0"`。仅开发期生效，但连公共 WiFi 时会暴露。建议改 `--host=127.0.0.1`。（待核实：是否刻意为真机联调而设。）

## 🟢 建议

### 8. `sandbox: false` 可考虑开启
main.cjs:695。preload 现在只用 `contextBridge` + `ipcRenderer`，理论上可以 `sandbox: true` 进一步收紧。纵深防御，低优先。

### 9. IPC handler 未校验 sender
main.cjs:829-849 不校验 `event.senderFrame`。当前只有一个可信窗口，风险低；`settings:save-api-key` 这类敏感 handler 建议加 sender 校验工具函数。

### 10. `loadAppSettings` 每次 IPC 重读盘
main.cjs:30-45, 202-216。建议加内存缓存，写时失效。性能微优化。

### 11. 启动顺序：窗口等后端就绪才出，冷启动白屏偏久
main.cjs:682-683 先 `await startBackend()` 再建窗口，健康检查超时 60 秒（main.cjs:178），期间用户看不到任何窗口。建议先建窗口显示"正在启动后端…"loading 态，再异步等后端就绪。

### 12. macOS `notarize: false` 但有 afterSign 公证脚本——确认未失效
package.json:98 关掉内置公证，由 afterSign `notarize.cjs` 接管（靠 `APPLE_*` 环境变量）。建议加注释说明，避免日后误开内置导致双重提交。（待核实：CI 里 `APPLE_*` 是否确实注入，否则脚本静默跳过 = 出未公证包。）

## 自动更新（electron-updater）专项

main.cjs:771-832 配置基本正确。两点提醒：
- **🟡 Windows 未签名 + 自动更新 = 危险组合**。electron-updater 在 Windows 上靠 sha512 校验下载完整性，但不校验 Authenticode 签名。mac 有公证签名兜底，Windows 这条链目前只靠 GitHub HTTPS + hash。长期上线前强烈建议买 Authenticode 证书（也顺带消 SmartScreen 警告）。
- **🟢 更新失败用户无感**。`error` 只进 console + Sentry，没 `sendToRenderer`。建议转发给渲染进程提示"更新失败，请手动下载"。

# 三、Python 后端审查（FastAPI + ffmpeg）

**总体印象**：架构清晰，B-router 重构后职责分层合理（routers / deps / 服务层），状态持久化用了 atomic temp+replace，OSS 分片上传有完整的 per-part 重试和 abort 清理，子进程调用全部用 list 形式（无 shell 注入），测试 103 passed。对单用户桌面后端来说，工程质量明显高于平均水平。

## 🔴 严重

### 1. 长视频抽帧把整段全分辨率帧一次性 load 进内存 → 弱机 OOM

`detection_service.py:371-403`（cv2 路径，默认）+ `detect_video:125-160`：

```python
frames, frame_times = self._extract_all_frames(...)  # 全部采样帧驻留 list
candidates = self._precheck_candidates(frames=frames, ...)  # 再追加底部区域
frames.clear()  # 直到这里才释放
```

cv2 路径返回全分辨率 BGR 帧。2 小时视频、`sampling_interval=2.0` ≈ 3600 帧 × ~6 MB/帧 → **峰值约 21 GB**，且 precheck 期间 `frames` 与 `candidates` 同时存在。ffmpeg 快路径缩到 540p（约 5.5 GB）但默认 `DET_FFMPEG_EXTRACT` 关闭。这正是「AV1 弱机兜底」担心的那类机器，必然 OOM 崩溃。

**建议**：改成流式处理——边解码边 precheck，只保留通过 precheck 的底部区域。ffmpeg 路径已是逐帧读取，把 precheck 放进 while 循环即可；cv2 路径同理在 `cap.read()` 循环里直接调 `_quick_subtitle_check`。

## 🟡 重要

### 2. ffmpeg / ffprobe 子进程无超时 → 单 worker 导出/探测可被永久挂死

`export_service.py:1107`（`_run_ffmpeg`）、`:866`（`_ensure_ffmpeg`）、`video_metadata.py:22`（`probe_video_metadata`）均无 `timeout`。`export_job_manager` 是 `max_workers=1`，一个损坏视频让 ffmpeg 卡住，之后所有导出任务排队卡死，且导出 runner 不检查取消信号，用户只能重启后端。

**建议**：所有 `subprocess.run` 加 `timeout=`（导出按时长估算，探测 30~60s），捕获 `TimeoutExpired` 转失败结果。注意 `capture_output=True` 超时杀进程后要 drain 管道避免 zombie。

### 3. `import_project_files` 在全局状态锁内做 ffprobe 子进程 + 网络请求 → 阻塞前端轮询

`routers/project.py:99-113`：`project_state_lock()` 内做 `import_videos_into_project`（内部 ffprobe）+ `fetch_platform_records`（网络 I/O）。`GET /api/project`（前端轮询）也要拿这把锁。对比 `import_direct_clip_files`（routers/project.py:162-174）把网络 fetch 放在锁外——同一 codebase 两种写法，证明锁外可行。

**建议**：探测和平台请求移到锁外，只在最后合并写入时短暂持锁。

### 4. 导出任务无法取消（取消回调被忽略）

`routers/project.py:329`：`def runner(progress_callback, _is_cancel_requested):`——参数名加下划线，runner 内从不查询。检测任务有完整取消链路，导出/上传一旦 running 就停不下来。

**建议**：在 clip 循环和 upload 循环边界检查 `is_cancel_requested()`；ffmpeg 层面配合 timeout 用 `Popen` + `terminate()` 实现真正中断。

### 5. CORS 全开 + 接受任意本地路径导入 → 浏览器侧 CSRF 风险

`api.py:33-38` + `routers/project.py:80-92`（JSON 模式 import 接受任意 `{"path": ...}`）+ `routers/videos.py:282-293`（`/stream` 直接吐 `video.file_path`）。恶意网页 JS 可向 `127.0.0.1:8000` 发 `POST /api/project/import` 导入任意本机视频，再 `GET /stream` 读出内容。

**建议**：同 Electron 报告第 2 条——收紧 origins + spawn env 注入 token + 中间件校验。

### 6. 缩略图接口对 `video_id`、`file_name` 无路径包含校验

`routers/videos.py:337-342` → `thumbnail_service.py:63`。同 Electron 报告第 1 条，`resolved.resolve()` 后断言在 `cache_root` 内再返回，并先用 state 校验 `video_id` 合法。

### 7. 明文 API key 落在工作目录 config.json，需确认未进打包产物

`backend/config.json` 含 `zhipu_api_key`（真实形态）。已确认：被 gitignore、`build_backend.py` 未打包它——不进 git 也不进 PyInstaller 产物。但本机磁盘仍明文驻留。

**待核实**：这把 key 是否就是 `26f50f0` 提到已轮换作废的那把？另：`detection_service.py:291-297` 的 `_load_config` 找的是 `cwd/config.json` 和 `repo_root/config.json`，并不包含 `backend/config.json`——路径逻辑与文件位置不一致，可能是 dead config。

### 8. `NamedTemporaryFile(delete=False)` 在序列化异常时泄漏临时文件

`storage.py:45-49`：`json.dump` 抛错则 temp 文件留在 workspace。**建议**：try/except 包住 dump，异常时 `tmp_path.unlink(missing_ok=True)` 再 re-raise。

## 🟢 建议

### 9. 死代码：`_fetch_all_around_records` / `_fetch_team_records` 不可达
`platform_client.py:461`、`:514`。`fetch_platform_records:260-263` 对所有类型都走 `_fetch_single_item_records`，约 130 行死代码，且 TF 团体过滤逻辑只在死方法里，易误导。建议删除或补说明。

### 10. 检测默认走慢路径（cv2 seek-per-sample），快路径藏在 env 后面

### 11. `@app.on_event("startup")` 已废弃

### 12. `APIError` 类定义了却从未被 raise

### 13. `_is_valid_athlete_name` 黑名单用子串匹配
`detection_service.py:896-911`。`"usa" in name_lower` 会误杀真名里含这些子串的运动员。建议按 token 匹配。
